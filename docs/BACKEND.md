# Бэкенд: проект v1

Черновик решения. Обсуждаем до того, как писать код.

## Топология

```
        Windows-машина                    Виртуалка в локальной сети
┌────────────────────────────┐      ┌──────────────────────────────┐
│  браузер                   │──WS──┤  gateway (Docker)            │
│                            │      │   ├── SQLite (том)           │
│  SketchUp   :8080          │◄─────┤   └── OpenRouter (интернет)  │
│  Rhino      :9890          │  ??? │                              │
│  Blender    :9876          │      └──────────────────────────────┘
└────────────────────────────┘
```

Знак вопроса — единственная неизвестная в схеме, и она важная: **мосты движков
живут на Windows-машине, а gateway будет на виртуалке**. Проверено 2026-07-25:
сейчас порты `8080 / 9890 / 9876` не слушает никто — движки просто не запущены.
Как только запустим, надо посмотреть, на каком интерфейсе они висят.

Два способа связать (решаем позже, в v1 движки не трогаем):

**А. Перевесить мосты на сетевой интерфейс.** Просто. Порты открыты в локальную
сеть — для хоумлаба приемлемо.

**Б. Агент на Windows, который сам звонит в gateway.** Тонкий процесс держит
исходящее соединение и проксирует к `localhost`. Входящие порты не нужны,
работает из любой сети, и это же станет основой десктопной обёртки.

Склоняюсь к **Б** как к цели и к **А** как к быстрому старту.

## Что входит в v1

1. **gateway** — реализует существующий интерфейс `Transport` из `@complex/protocol`.
2. **SQLite** — сессии, переписка, графы, задачи. Переживает перезапуск контейнера.
3. **Живая модель** через OpenRouter: настоящий ответ вместо шаблона мока.
4. **Docker Compose** на `.96`.
5. **`WsTransport`** во фронтенде вместо `MockTransport` — одна строка в `transport.ts`.

## Что НЕ входит в v1

Движки, база знаний, CLI-агенты, загрузка файлов, авторизация. Каждое — отдельный
заход, и каждое проще делать поверх работающего gateway, чем одновременно с ним.

## Протокол связи

Одно веб-сокет-соединение и конверт вида:

```jsonc
// запрос
{ "id": "7", "method": "openSession", "params": { "sessionId": "s-014" } }
// ответ
{ "id": "7", "result": { … } }
// событие потока (стриминг ответа, прогресс задачи)
{ "id": "7", "event": { "type": "token", "text": "Прин" } }
```

Методы — ровно те, что уже описаны в `Transport`. Асинхронные итераторы
(`sendMessage`, `runJob`) превращаются в поток событий с тем же `id`; клиент
собирает их обратно в итератор. Отдельный REST не нужен — меньше движущихся частей.

## Хранение

SQLite, схема повторяет типы протокола:

| таблица | назначение |
|---|---|
| `sessions` | id, code, title, project, engine, status, даты, `deleted_at` для корзины |
| `messages` | id, session_id, роль, текст, модель, дата |
| `tool_calls` | id, message_id, имя, движок, статус, код, результат, длительность |
| `graphs` | session_id, документ графа, дата |
| `jobs` | id, session_id, спецификация, статус, прогресс |

Поиск по переписке — обычный `LIKE` на старте; если станет мало, у SQLite есть
полнотекстовый поиск FTS5, переход недорогой.

## Модели

OpenRouter даёт один ключ на множество моделей, включая Claude. Ключ живёт в
`.env` на виртуалке и в репозиторий не попадает. Стриминг приходит по SSE и
пересылается в веб-сокет как события `token`.

## Порядок работ

1. Скелет `services/gateway`, `Transport` поверх веб-сокета, данные в памяти.
   Фронт переключается на `WsTransport`. Мок остаётся как запасной вариант.
2. SQLite вместо памяти.
3. OpenRouter: настоящий стриминг.
4. Docker Compose, разворачивание на `.96`.
5. Раздача собранного фронтенда с виртуалки.

Каждый шаг проверяем по `docs/CHECKS.md` — сценарии приёмки уже написаны и не
зависят от того, кто отдаёт данные. Это и есть проверка, что подмена транспорта
прошла без потерь.

## Открытые вопросы

- Стек gateway: Node/TypeScript или Python.
- Где собирается и раздаётся фронтенд в рабочем режиме.
- Способ связи с движками — А или Б, решаем к шагу «движки».
